SECTION 2: THE DOCKERFILE — PRODUCTION-GRADE BLUEPRINT
2.1 Base Image Selection: The Critical First Decision
The rocker/shiny-verse family is the industry standard for R Shiny containers. Your options:

Image	Size	Use Case
rocker/r-ver:4.5.0	~800MB	Minimal R runtime; build everything yourself
rocker/tidyverse:4.5.0	~1.8GB	Pre-installed tidyverse; good for data-heavy apps
rocker/shiny:4.5.0	~1.5GB	Shiny Server pre-configured
rocker/shiny-verse:4.5.0	~2GB	Shiny + tidyverse; recommended for your app
Why shiny-verse: Your app uses ggplot2, dplyr, FactoMineR, and shiny. The shiny-verse image includes Shiny Server and the tidyverse pre-installed, saving build time and reducing the chance of system dependency conflicts.

2.2 Layer Ordering: The Cache Optimization Secret
Docker builds images layer by layer. Order matters for rebuild speed:

text
LAYER ORDER (least to most frequently changing):
─────────────────────────────────────────────────
1. Base image          ← Never changes
2. System dependencies ← Rarely changes
3. R packages          ← Changes when renv.lock updates
4. Application code    ← Changes on every git push
5. Entrypoint/CMD      ← Rarely changes
Why this matters: When you change one line of app.R, Docker reuses cached layers for steps 1-3 and only rebuilds steps 4-5. This reduces build time from ~15 minutes to ~30 seconds.

2.4 Dependency Management with renv (Non-Negotiable)
Never install packages with install.packages() inside the Dockerfile without version pinning. This is a recipe for disaster.

The renv workflow:

Local development: Run renv::init() in your project to create a renv.lock file

Docker build: Copy renv.lock and run renv::restore() inside the container

Result: Exact package versions (e.g., FactoMineR_2.11 not just FactoMineR)

Why this is critical for your app: FAMD results depend on the exact implementation of PCA/FAMD. A minor FactoMineR update could change your loadings and therefore your weighted scores. renv freezes the statistical methodology.

2.5 The Multi-Stage Build Pattern
Multi-stage builds use one image to compile/install and a second (smaller) image to run.

Why for your app:

Build stage: Full R + compilers + build tools (~2.5GB)

Runtime stage: Only R + compiled packages (~1.2GB)

Result: 50% smaller image, fewer vulnerabilities, faster pulls

SECTION 4: DEPLOYMENT ARCHITECTURES
4.1 Option A: ShinyProxy — The Enterprise Standard
ShinyProxy is the gold standard for production Shiny deployments.

How it works:

A Java-based orchestration layer sits between users and your app

Each user session gets its own dedicated container

Containers are created on-demand and destroyed when sessions end

Built-in authentication (LDAP, OAuth, SAML)

Pros for your app:

Complete resource isolation — heavy FAMD computations don't affect other users

Automatic scaling — containers spin up as users arrive

Professional authentication — perfect if you want to share with colleagues

Cost-effective — containers only exist when users are active

Cons:

Requires Java runtime (additional system dependency)

More complex setup than a single container

Minimum server requirements: Linux (Ubuntu 20.04+), 8GB RAM minimum, 16GB+ recommended for production.

4.2 Option B: Docker Compose — The Simple Production Path
Best for: Single-server deployments, internal tools, or low-traffic scenarios.

What you get:

A single docker-compose.yaml file defines your app + reverse proxy + optional database

Nginx or Traefik handles SSL termination and routing

docker compose up -d starts everything

Your compose stack:

4.3 Option C: Kubernetes — The Cloud-Native Path
Best for: High-traffic, multi-region, or enterprise cloud deployments.

Why Kubernetes for your app:

Horizontal scaling — add replicas as traffic grows

Rolling updates — zero-downtime deployments

Self-healing — crashed containers auto-restart

Cloud-agnostic — run on AWS EKS, GCP GKE, Azure AKS, or on-prem

Minimum setup:

Container image in a registry (Docker Hub, GitHub Container Registry, ECR)

Deployment YAML defining replicas, resources, and health checks

Service YAML exposing the app (ClusterIP + Ingress)

4.4 Option D: Posit Connect / shinyapps.io — The Managed Path
If you want to avoid Docker entirely:

shinyapps.io is Posit's managed hosting

One-command deployment: rsconnect::deployApp()

Free tier available; paid tiers for production

Why you might still want Docker:

shinyapps.io has package installation limits and timeout constraints

No control over the underlying R version

Harder to reproduce exactly if you need to migrate

SECTION 5: CI/CD PIPELINE
5.1 GitHub Actions (Recommended for Public Repos)
What it does: Automatically builds and pushes your Docker image on every git push to main.

The workflow:

Developer pushes code to GitHub

GitHub Actions triggers

Builds Docker image using the Dockerfile

Runs tests (does the app start? do plots render?)

Pushes image to GitHub Container Registry (ghcr.io)

(Optional) Deploys to your server via SSH or webhook

Why this is impressive: Your deployment is fully automated. No manual docker build or docker push commands.

5.2 GitLab CI (Alternative)
Similar workflow with GitLab's built-in container registry.

5.3 Deployment Strategies
Strategy	Description	Best For
Rolling Update	Gradually replace old containers with new ones	Zero-downtime production
Blue-Green	Run new version alongside old; switch traffic when ready	Risk-averse deployments
Canary	Send 5% of traffic to new version; monitor for errors	High-stakes apps
SECTION 6: MONITORING & OBSERVABILITY
6.1 Health Checks
Your container must report its health to the orchestrator:

dockerfile
HEALTHCHECK --interval=30s --timeout=3s --start-period=5s --retries=3 \
  CMD curl -f http://localhost:3838/ || exit 1
Why: Kubernetes and ShinyProxy use health checks to restart unhealthy containers automatically.

6.2 Logging Strategy
Golden rule: Write logs to stdout, not to files.

r
# In your Shiny app
options(shiny.trace = TRUE)  # For development
# Production: use structured logging
cat(sprintf('{"level":"info","message":"User %s viewed plot","timestamp":"%s"}\n',
            session$user, Sys.time()))
Why: Docker captures stdout. Your logs go to docker logs or your log aggregator (ELK, Datadog, Grafana Loki).

6.3 Performance Metrics to Track
Metric	Why It Matters
Startup time	Users won't wait >10 seconds
Memory usage	FAMD + bootstrapping can spike memory
Request latency	Slow plots frustrate users
Error rate	Track 500 errors from the app
SECTION 7: SECURITY HARDENING
7.1 Non-Negotiable Security Practices
Practice	Why	How
Run as non-root	Root inside container = host risk	USER shiny in Dockerfile
Use specific tags	latest is unpredictable	rocker/shiny-verse:4.5.0 not latest
Scan for vulnerabilities	Known CVEs in base images	docker scan or Trivy
Minimal packages	Every package is an attack surface	Only install what you need
SSL/TLS	Encrypt traffic	Nginx + Let's Encrypt
7.2 The rocker Security Note
The rocker/shiny-verse image runs the Shiny Server as the shiny user by default. Do not override this unless you have a specific reason.

SECTION 8: PERFORMANCE OPTIMIZATION
8.1 Pre-computation Strategy (Reinforced)
Critical for your app: The FAMD is computationally intensive. Do not run it inside the container on startup.

The correct approach:

Run FAMD locally once

Extract the loadings (coefficients)

Save as data/famd_loadings.rds

The Shiny app only loads the .rds and applies the multiplication

Result: Container startup time drops from ~15 seconds to ~2 seconds.

8.2 Caching in Shiny
Use shiny::bindCache() on expensive render functions:

r
output$bootstrapPlot <- renderPlot({
  # Expensive bootstrap computation
}) %>% bindCache(input$k_param, input$competition_filter)
Why: The bootstrap doesn't re-run unless the user changes the K-parameter or competition filter.

8.3 Resource Limits
Always set resource limits in your deployment:

yaml
# docker-compose.yaml
services:
  app:
    deploy:
      resources:
        limits:
          memory: 2G
          cpus: '1.0'
        reservations:
          memory: 512M
          cpus: '0.5'
Why: Prevents a single user from consuming all server resources.
